# 会话维度与对话历史；journal 写盘归并

T7（Issue #7）把「回放」从**运行 trace** 升级成**对话历史**。ADR-0008 当时把「journal 里没有用户输入」记作已知取舍，并写明「若日后确实需要，应当新增一个 run 元事件来承载请求」——本 ADR 就是来还这笔债的，同时记录会话维度、`category` 分流、以及写盘归并这几个判断。

## 决策

**1. 引入 thread（会话）维度，`thread_id` 用「给了就用，没给就生成」的语义。** 编排器接受可选的 `thread_id`，缺省自生；网关把它交给 `run_plan_exec` 与 `RunJournal`，所以前端拿到的 id 一定能查到对应记录。前端本地生成（`crypto.randomUUID`，非安全上下文下退回随机十六进制）并记在 localStorage，因此不必先请求「建会话」。这与参照项目 DeerFlow 的 `resolve_thread_id()` 语义一致（它那边 id 存在 URL 里，我们没有按会话路由的页面，所以存 localStorage）。

**2. 会话不是实体，是 journal 按 `thread_id` 的分组。** 没有 conversations 表，也没有「建会话」端点——「开启新对话」只是本地换一个 id，会话由第一次运行落进 journal 时自然形成。列表、标题、摘要全部从 journal 推导：标题取会话**第一次运行**的用户请求截断，摘要（`preview`）取**最近一次运行**里最后一段助手正文。

**3. 一个会话一个文件**：`data/journal/<thread_id>/journal.jsonl`（外加 `meta.json` 存自定义标题）。

T3 的布局是「一次运行一个文件」（`<thread_id>/<run_id>.jsonl`，参照项目也是那样）。**那个设计是从 T3 继承的，不是为 T7 选的，而且 T7 之后它的好处基本消失了**：我们**从来不单独读某一次运行**（`GET /threads/{tid}/journal` 永远整段读，单 run 的端点在实现时就没有消费者），而它把跨运行的顺序搞难了——文件内顺理成章的行序没了，得逐个打开文件读 `run_start.started_at` 才能排序，文件名又是随机 hex 靠不住。

合成一个文件后：**行序天然就是跨运行的全序**；标题、摘要、运行次数、最近一次运行的 id 全都从**同一次读取**里得到；`RunJournal` 连 `run_id` 都不需要了（身份由 `run_start` 事件自带）；store 接口里的 `runs()` 与 `JournalRun` 整个消失。

**代价是同一会话的两次运行并发写会交错。** UI 在流式期间禁用输入，所以当前不会发生；真要支持并发，要么按 run 再拆文件，要么像参照项目那样用「一个会话同时只允许一个活跃 run」的约束挡住（它用 DB 的部分唯一索引实现）。

**顺带修掉一处不一致**：会话列表的判据只有「有没有 `journal.jsonl`」。曾经写成「没有 `run_start` 就不算会话」，那会让数据**存在却查不到**（`load` 读得到、`threads` 不列出）。

**4. 新增 `RunStartEvent` 作为每个 run 的首个事件**，承载 `run_id` / `thread_id` / `request` / `started_at`。`PlanEvent` 因此**不再带 `run_id`**——T3 把它挂在 `plan` 上时 ADR-0008 就标明那是权宜之计。它还有一个位置上的理由：在调用 planner **之前**产出，客户端不必等规划完就知道自己在哪个会话，planner 挂掉时这次运行也留得下痕迹。

**5. `category` 是「给消费者路由用的桶」，不是排他分区。** 沿用参照项目的定义（其 store 契约原文即 "category: Consumer-routing bucket"）：

| category | 事件 | 为什么 |
|---|---|---|
| `message` | `run_start`、`messages`、`task_end` | 承载对话内容：用户请求、助手正文、任务的产出与成败 |
| `trace` | `plan`、`task_start`、`replan`、`summary` | 只讲编排过程 |

于是**对话投影 = 过滤 `category == "message"`；trace 投影 = 全部事件**（面板要靠 `messages` 里的工具调用行与正文才能重建）。这处不对称是有意的，不是分类不干净。

**6. journal 落盘前做写盘归并**（`compaction.py`）：同一个任务、同一份 metadata 的**全部纯文本增量**归并成一条。理由见下节实测。归并**只影响落盘**——tee 仍把原事件原样透传给 SSE。

**7. 前端重建会话时拉整段会话的完整事件，喂给与实时同一个 reducer。** 这是实现中的一个**偏离**：原计划让前端分两次拉（`/messages` 对话投影 + 最近一次运行的 trace），但这两段**本来就重叠**——`run_start` 与 `messages` 同时在两个桶里——分开拉再依次喂会让用户气泡重复、时间线顺序错乱（`task_start` 行会跑到工具行后面）。改成一次拉全（`GET /threads/{tid}/journal`）之后，「历史与实时逐字一致」由构造保证，不需要任何拼接逻辑。`GET /threads/{tid}/messages` 仍然保留，作为服务端侧的对话投影，`preview` 就是它的实际消费者。

**8. 删除会话是真删**（连带磁盘上的目录），不做回收站。删除不可逆，所以前端必须有确认弹窗。

**9. store 同时管事件与会话元数据。** 重命名需要一处**可变**存储，而事件流是纯追加的，给不了。参照项目为此单开一张 `threads_meta` 表；我们只有一个标题要存，为它再加一层接口与配置不值当。代价是每个实现都要多实现几个方法——两个实现下可以接受，但**这是本 ADR 里最可能被后人质疑的一处**：如果将来会话元数据长起来（置顶、标签、成员），应当把它拆成独立的 store。

## 后果

- **写盘归并的收益是数量级的，而且元凶不是正文。** 实测一次运行 70204 字节：`messages` 事件占 68077（96%），其中**正文只有 266 字节，metadata 有 39264 字节——148 倍**。所以「不存文本增量」是治错了地方。
- **归并比例取决于这次运行有几轮 LLM 调用，不是一个固定倍数**（因为粒度就是「同一个任务 + 同一份 metadata」，每轮调用各留一条）。实测两例：一个两任务并行、各自一次 LLM 调用就跑完的运行，224882 字节 → 约 2KB（240 条 → 3 条，~1%）；一个带工具调用、多轮 LLM 调用的单任务运行，34358 字节 → 11487 字节（39 条 → 15 条，~33%）。**剩下的条目都是真的不同的东西**——工具调用参数、工具结果、以及携带 `usage_metadata` 的纯元数据帧（`chunk_position` 的 first/last 标记）——它们不该被合并。
- **归并的等价性可证明，并且有测试兜底。** 前端 reducer 对文本只做「按 `task_id` 追加」，气泡顺序由 `task_start` 决定（与文本到达序无关），工具行来自**不参与归并**的 tool chunk。测试不用「reducer 的 Python 复刻」表达等价（那只是自说自话），而是两条性质断言：每个任务的正文按序拼接后逐字相同、不可归并的事件子序列逐条相同。
- **归并是有损的**：逐 token 边界与并行交错顺序不再保留，事后还原不出「token 是怎么一个个来的」。这是拿体积换的；可观测状态不受影响。参照项目走得更远——它**根本不存 token delta**（只存 `on_llm_end` 的完整消息），代价是刷新后看不到「正在生成的那半条」。我们保留增量，所以历史与实时逐字一致。
- **归并让崩溃窗口变大，已用提交点补偿。** 缓冲条目变少 → 按条目数计的 `flush_threshold` 很少触发 → 只靠阈值的话崩在中途会丢掉整次运行。补偿是在 `TaskEndEvent` 之后**强制 flush**（任务做完是天然的提交点），把窗口限制在单个任务内。
- **`seq` 变成「严格递增但有跳号」**：被归并掉的编号就此空缺。它表达顺序，不是计数。
- **checkpoint 的 thread 坐标升到了会话级**：`{会话}:{运行}:{任务}`（`task_thread_id`）。原先只是 `{run_id}:{task_id}`——那是 T3 定的，那时还没有会话层。加会话这一段不是为了好看，而是因为**不加就删不干净**：`DELETE /threads/{tid}` 真删了 journal，却没有任何东西能把会话反查回它的 run_id 集合，于是那些 checkpoint 只能等保留策略（默认 7 天）才扫得到。实测当时 37 个 checkpoint thread 里有 25 个的会话记录已经不存在了。现在删除会话会按前缀连带清理（`delete_session_checkpoints`，前缀带分隔符以免误伤 `abc` / `abcd`），清理失败只记日志——会话本身已经删掉了，为一次收尾失败报错只会让人以为没删掉。代价：旧格式的 checkpoint 无法被前缀匹配到，只能等保留策略扫走。
- **长会话仍整段传输**：`GET /threads/{tid}/journal` 没有分页。归并后规模可控（一次运行约 KB 级），但会话很长时要补 `before_seq` 分页——参照项目是 backward-only 分页 + 无限滚动。
