# 技能：仓库源目录 → 只读视图 → 提示词清单

`/skills` 这个挂载点从 T4 起就在，一直是只读，但**从来没有生产者**——ADR-0012 当年把它写成一句
说明：「全局共享的，不随会话建，也还没有生产者」。本片给它接上第一个生产者。

目的是让 agent 有一套**可复用、可 review、可版本化**的「做事方法」：仓库里放技能目录，启动期投影到
`/skills` 只读视图，提示词里只列清单，模型需要时自己 `read_file` 去读全文。

## 决策

**1. 技能来自仓库源目录，启动期镜像到 `/skills` 的宿主目录。**

源是仓库根的 `skills/<名>/SKILL.md`，人工维护、进版本控制、能 review；视图是
`backend/.evaai/skills-view/`，运行期数据、已被 gitignore。`.gitignore` 早就忽略 `.evaai/`，所以
这个分工是天然的，不用额外规定。

分成两层而不是直接把源目录挂上去，是为了让模型的写入面仍然只有那一个**只读**挂载，而「技能从哪来」
以后可以换（比如从别处取）而不动沙箱那一层。

**投影是镜像**：源是唯一真相，源里删掉的技能要从视图里一并消失。不这么做的话，第一次投影之后视图
就开始自己长东西——「从仓库移走」永远不生效，而那是这类同步最经典的坑。

**没有任何技能时不创建视图目录**；最后一个技能被移走后，空掉的视图会被删掉。这兑现了 ADR-0012 那句
「它如实报『不存在』比造个空目录好」：模型看到的目录里**只有真能用的技能**。

**2. 技能正文**不进**提示词。**

提示词里每个技能只有三样：`name`、`description`、`location`。模型判断相关时**自己**用
`read_file` 打开 `/skills/<名>/SKILL.md` 读全文，再照着做。参照项目也是这个形状，理由是
**让 system prompt 保持静态**：它随技能**个数**缓慢增长，而不是随技能正文的体量膨胀；而且改一个
技能的正文不必让整个前缀缓存失效。

代价是「用上一个技能」要多一轮工具调用。接受——那一轮还顺便让模型读到了完整、未经摘要的步骤。

附件（模板、参考文件、脚本）跟着目录一起投影，模型可以用现成的 `read_file` 读它们。
**执行**不在本片：那要等 T15 的容器沙箱，现在跑脚本 = 在宿主上跑。

**3. 技能名的权威是**目录名**，frontmatter 的 `name` 必须与之一致。**

不一致就跳过并记警告。这与工具注册表那条既有规矩同形（`name` 必须与工具自己的 `.name` 一致），
理由也一样：名字决定虚拟路径、也决定技能之间怎么区分，两个来源分歧时症状是「明明在那儿却调不到」。

**名字允许中文**，禁的是会造成歧义或越界的东西：`/`、`\`、`..`、空白、控制字符、首尾的点。
本项目的提示词全是中文，禁中文会很意外；而 `..` 这类是真危险（它要当**路径段**用）。

**4. 坏技能：启动期**响亮地跳过**。**

不拒绝启动，也不静默——记一条警告，点名是哪个目录、差在哪里，服务照常起，那个技能只是不生效。

这是**刻意偏离参照项目**的：它解析失败时静默返回 `None`（技能就是不存在）。静默失效正是本项目一贯
拒绝的失败形状——目录明明在那儿却不生效、而日志里一个字都没有，那种问题只能靠猜。

与「`config.yaml` 的工具写错就拒绝启动」也不矛盾：那是因为**工具是 agent 的能力边界、没有隐藏的
默认集**（ADR-0012），而技能是**可选内容**。同理，它与 MCP 那条「server 起不来只警告」是同一个性格。

**5. 清单拼进 `system_prompt` 字符串，不走中间件。**

这不是口味，是**被两条既有断言逼出来的**：`tests/test_react.py` 硬编码了默认中间件链的六个类名，
`tests/test_lead_agent_memory.py` 断言模型收到 10 条消息。往链里加中间件会把前者顶破，往 messages
里注入一条会把后者顶破；而拼进 `system_prompt` **两条都不动**（system 那条只是变长，条数不变）。

附带的好处是提示词的可预测性：技能集在一次运行里固定，拼出来的字节也就固定。

**6. 子 agent 也看得到技能；planner / replanner 不看。**

技能是「一件事该怎么做」的指北，而子 agent 干的正是具体的事，所以主图、子图、Plan-Exec 执行单元
三条路径都拼同一段清单。

planner / replanner 例外：它们走 `with_structured_output`、不调工具，给了也读不了——与
`extra_tools` 只喂执行单元是同一条口径。

**7. 技能的改动要重启才生效。**

与既有的「配置无热重载」同一立场。技能集在启动期定下来，运行期不再扫——它让「这次运行能看到哪些
技能」成为一件确定的事。

## 后果

- **`/skills` 从「不存在」变成「存在」**（有技能时）。ADR-0012 里那句「还没有生产者」到此解除；
  `sandbox.py` 的注释跟着改。
- **`/skills` 的宿主路径有了单一来源**：`sandbox.skills_view_root()`。它必须与 `MOUNTS` 里那条
  `Mount("/skills", parts=("skills-view",))` 始终一致——两处各写一份迟早漂移。
- **提示词里多了一段**，但只在有技能时；没有技能时 `_prompt()` 逐字节原样返回基础提示词。
- **`extensions_config.json` 的 `skills` 仍然空着**。本片**完全不读它**——技能源目录就是唯一真相，
  「停用某个技能」= 把那个目录移走。为一层还不存在的需求把它用起来，与 ADR-0012 / 0017 两轮纠结的
  「别把半成品坐实成契约」是同一个毛病。
- **`lifespan` 会写磁盘**（投影）。所以跑 lifespan 的测试必须把它换掉——否则测试会开始往真实的
  `backend/.evaai/` 写东西。

## 不做 / 范围外

- **`/skill-name` 显式激活**：参照项目那一大块（中间件 + 隐藏 HumanMessage 注入 + 幂等去重 +
  secrets 绑定）依赖我们没有的地基——没有 slash 命令解析、没有 secrets、没有 UI 入口。不做也不影响
  上面那条「模型自己读」的路。
- **`allowed-tools` 工具收窄**：它要配合「激活」才有意义（参照项目的设计里，技能只是被列在提示词中
  **不生效**），而那意味着给模型可见工具做一层动态过滤——一个独立机制。
- **技能的执行**（脚本、附件里的可运行内容）：等 T15 的容器沙箱。
- **热加载**：见决策 #7。
- **多用户隔离与可插拔存储**（参照项目的 `SkillStorage`、per-user custom 目录、四分类）：
  单用户用不上。「技能从哪来」以后要换的话，`project_skills(src_root, view_root)` 那两个显式路径
  就是缝。
