# 工具注册表与文件沙箱（虚拟路径 + 四个挂载点）

> **2026-10-10 部分修正**：T17 把**沙箱机制与文件工具**搬进了 harness（`evaharness.sandbox`，见 [ADR-0020](0020-sandbox-in-harness.md)），宿主根与挂载表改成从运行上下文注入。本文的核心决策**一条没变**——虚拟路径、四个挂载点、两层校验、失败一律 raise——变的是它们住哪一层，以及「挂载表是业务决定」这句被修正成「框架给默认惯例、部署拍板根在哪儿」。**工具注册表**留在 app，那条决策照旧。

T4 之前 agent 只会一件事：`get_current_time`。工具列表是 `app.py` 里一行硬编码
`BUSINESS_TOOLS = [get_current_time]`——**扩大 agent 能力的手段本身要改框架代码**。而 agent
一旦能写盘，就必须有边界：没有边界的话，一次幻觉就能改坏仓库、读到 `.env` 里的两个 API key。

本 ADR 记录两件事：工具从哪来（配置 + 反射），以及模型能碰哪些文件（虚拟路径 + 挂载点）。

## 决策

**1. 工具的注册表是 `config.yaml` 的 `tools:`，`use` 是 `module.path:attr`。**

加一个工具的完整动作 = 写一个 `@tool`（或一个返回工具的工厂）+ 加一项配置。**不改任何
Python 框架代码**——这是 Issue #3 的验收标准，也是本片的立身之本。反射走
`evaharness.reflection.resolve_variable`（新增）：工具是 `BaseTool` 的**实例**，现有的
`resolve_class` 会因 `isinstance(value, type)` 不成立而拒掉它们，所以必须并列一个认实例的。
`resolve_class` 改成委托给它，一处 import 逻辑、一份错误文案。

**不做包扫描**（`app/tools/` 下自动收集）：那会让「到底装了几个工具」变成读代码才知道的事，
顺序也不确定，而且没法单独禁用某一个。显式列表的代价是写一行，收益是可以一眼读出来。

**2. `use` 可以指向实例，也可以指向工厂；额外键是工厂的关键字参数。**

这条是**偏离 DeerFlow 的关键处**。DeerFlow 把工具私有参数（`max_results` / `timeout`）留给
工具**体内**的全局 `get_app_config().get_tool_config(name)` 去读。EvaAI 不走这条路：

- ADR-0011 刚刚把隐式全局按下去（跨请求状态必须显式注入），再种一个进程全局是往回走；
- 全局让工具不可单测——测试得先设全局才能调工具；
- 工厂把参数在**构建期**绑成闭包，工具实例因此是自足的：调用期不读任何外部输入。

代价是 `extra` 必须有归宿：写成工厂不接受的键会抛 `TypeError`（启动期就炸），而不是被静默
忽略。这是选工厂形态、而不是把额外键禁掉的原因——**没有会被静默吞掉的配置**。

**2b. `TAVILY_API_KEY` 可选，缺了走无 key 模式。**

本来设计成「缺 key 就拒绝启动」，理由是「服务起得来、每次搜索只回一句错误」最难查。**实测
推翻了这个前提**：Tavily 的无 key 模式是真能用的（返回真实结果，只是有速率上限），不是每次
都失败。而拒绝启动的代价很实：模板配置要求第一次上手的人先去申请一个第三方 key 才能把服务
跑起来。所以改成可选，真撞上速率上限时 Tavily 抛的异常会被中间件转成可见的工具错误。

教训值得记：**「缺配置的失败模式」要按实测写，不能按想象写**——两者的结论正好相反。

**3. 启动期严格校验，任何一项不合格就拒绝启动。**

- `name` 必须与工具自身的 `.name` 一致（DeerFlow 只打一条 warning，后果是模型调用一个路由里
  不存在的名字）；
- 全表不许**重名**——`create_agent` 对此是**静默接受**的（ADR-0011 记的已知盲区），注册表
  是唯一能在启动期看见它的位置；
- 不许占用 `task`（主 Agent 派发子 agent 的保留名，撞名会把派发路由到业务工具上）；
- `tools:` 为空也拒绝启动：**没有隐藏的默认集**。工具是 agent 的能力边界，不该有两个来源
  （代码常量 + 配置）而其中一个是隐形的。这偏离了 `JournalConfig.dir is None` 那条「缺省即
  用默认」的惯例，因为那个缺省的后果只是「journal 落在默认目录」，而这里的后果是
  「助手什么都不会」——后者难查得多。

**4. 文件操作走虚拟路径，宿主目录藏在四个挂载点后面。**

| 虚拟 | 宿主 | 权限 |
|---|---|---|
| `/workspace` | `.evaai/user/{会话}/workspace`（相对路径的落点） | 读写 |
| `/output` | `.evaai/user/{会话}/output` | 读写 |
| `/input` | `.evaai/user/{会话}/input` | **只读** |
| `/skills` | `.evaai/skills-view`（全局） | **只读** |

**宿主绝对路径永远不进模型上下文**：①信息泄漏（暴露本机布局）；②不可移植（换台机器就不存在，
而对话里学到的路径会留在上下文里）；③`OSError` 的消息天然带宿主路径。所以沙箱层自己用虚拟
路径措辞，而不是把原始异常往上抛。

**为什么 input / skills 只读**：前者是用户上传的原件，改坏不可逆——要改就复制到 workspace 改；
后者是 agent 的行为指南，能被自己改写的技能等于把提示注入面交给模型。`/input` 只读是**偏离
DeerFlow** 的（它把 uploads 当可写），代价只是模型多一次复制。

**会话的三个目录在第一条消息上就建出来**（`Sandbox.__init__` 里幂等 mkdir，路由在解析完
`thread_id` 后调 `ensure_session_dirs`）。这条是验收时补的：原来只靠 `write_file` 顺手建父
目录，于是新会话的第一次 `ls` 返回「不存在」，模型据此会判定**工作台不可用**——它只是空的。
工具的返回值是模型唯一能看到的世界，所以「空」与「不存在」必须分得开。

建在**第一条消息**而不是第一次文件操作，是为了让用户能在对话开始前把要处理的文件放进
`/input`，也让「这个会话有没有文件空间」不取决于模型想没想起来调工具。代价是纯聊天的会话
也会留下三个空目录——这与下面「删会话不删文件」那条债叠在一起，见遗留债。
`/skills` 不在其中（全局、还没有生产者），它如实报「不存在」比造个空目录好。

**5. 会话 id 从运行上下文取，认两种形状；取不到就抛。**

`session_id(runtime)`（加在 `evaharness.agents.middlewares.context`，与 `thread_bucket` 同处）
的对象分支读 `LeadContext.session_id`；dict 分支（Plan-Exec 的执行单元只有坐标
`{会话}:{运行}:{任务}`）取第一段——这条切法复用的是一个既有契约（坐标必以 `{会话}:` 开头，
`delete_session_checkpoints` 的前缀扫描依赖同一个事实），不是猜。可靠前提是会话 id 不可能含
`:`。

取不到**抛**而不兜底：分桶兜错只是账本混在一起，路径兜错会把两个会话的文件写进同一个目录，
而且不可逆。

**6. 失败一律 raise，工具层不返回 `Error: ...` 字符串。**

`ToolErrorHandlingMiddleware` 本来就是干这个的，而且它转出来的 `ToolMessage` 带
`status="error"`，模型与框架都认得出；一条内容是 `"Error: ..."`的正常返回值在摘要压缩时与
正文没有区别。工具里再兜一次会让失败有**两种**形状。偏离 DeerFlow（它两边都做）。

## 沙箱的防护层次

1. **词法**：归一 `\` → `/`、拒绝 `..` 整段、拒绝盘符 / `~` / UNC / NUL。在做任何 I/O 之前
   拒掉，才有干净的「虚拟路径」错误消息。
2. **解析后**：`Path.resolve()` 之后再比一次包含性。**这一层不能省**——词法层看不出符号链接
   与 Windows junction 逃逸，而 junction 连管理员权限都不需要。比较用 `normcase`：Windows 上
   大小写敏感的字符串比较会把合法路径判成越权（假阳性在安全侧，但那是「明明写不进去」这种
   很怪的 bug）。
3. **渲染**：工具输出的路径由我们自己拼虚拟路径，遮蔽只作最后一道网。

实测记录一个**踩过的坑**：宿主根必须在构造时 `resolve()` 一次。不规范化的话，后续每次比较
都在拿「解析过的子路径」比「没解析过的根」——Windows 的 `%TEMP%` 常带 8.3 短名
（`ADMINI~1` vs `Administrator`），于是所有挂载点都判成「不含」，**虚拟路径渲染会静默退化成
宿主路径**。这个 bug 是端到端探针抓到的，单元测试当时是全绿的。

## 后果

- **工具链路的形状没变**：`create_agent(tools=...)` 依旧在请求期 `bind_tools`，本片没有引入
  任何启动期建好的图。每请求建图（ADR-0011）不受影响。
- **`BUSINESS_TOOLS` 常量消失**，`business_tools` 成为启动期产物。
- **补上了 ADR-0011 的一个盲区**：重名工具从「静默接受」变成「启动失败」。剩下的
  `state_schema` / `context_schema` 传错仍然抓不到（smoke build 的注释要跟着更新）。
- **`.evaai/` 成为运行期目录**（已 gitignore），与 `data/` 并列。
- **`input` 只读**是偏离 DeerFlow 的一处：如果将来要放开，改的是 `MOUNTS` 表里一个布尔值。
- **工具输出的上限**：读 16k 字符、写 80KB、glob 200 条、grep 100 行、fetch 4096 字符。
  这些数字按**字符**算而不是按行，因为中文一个字约一个 token——照抄英文项目的预算会超。

## 偏离 DeerFlow 的清单（便于日后对照）

| 处 | DeerFlow | EvaAI | 为什么 |
|---|---|---|---|
| 工具私有参数 | 全局 `get_app_config()` | 工厂闭包 | ADR-0011 不许隐式全局 |
| `name` 不一致 | warning | 拒绝启动 | 后果是模型调不到，不是风格问题 |
| `str_replace` 唯一性 | docstring 说唯一，代码替换第一处 | **真的强制**唯一，否则不动文件 | 静默改错文件不可逆 |
| `input` 权限 | 可写 | 只读 | 原件改坏不可逆 |
| 失败形态 | 字符串 + 中间件兜底 | 只 raise | 一种形状 |
| `use_readability` | 默认 True | 默认 **False** | 见下 |
| 无结果 | `{"error": "No results found"}` | 空列表 | 200-OK 里塞 error 与「失败就 raise」自相矛盾 |
| read-before-write | 有（中间件记读取哈希） | **不做** | 单人本地、刚写完就改是主路径 |

## 硬约束

- **工具跨请求共享**（ADR-0011），所以工具实例上不许缓存任何东西：`Sandbox`、Tavily 客户端、
  `httpx.AsyncClient` 全部每次调用现建。失去连接池对个人助手是可接受的代价。
- **`readabilipy` 走 Node 那条路要它自带的 `node_modules`**。实测本机（含 DeerFlow 自己的
  venv）那份不存在，而 Node v24 在——于是 `use_readability=True` 会在**请求路径上**触发一次
  `npm install`（要外网，失败还会每次重试）。所以默认关，走纯 Python 抽取；Jina 服务端本来
  就已经做过一次正文提取。想要 Readability.js 的质量就在配置里打开。

## 不做 / 范围外

- **bash 工具**：DeerFlow 自己的 docstring 就写着「这不是安全边界」，而且本机是 Windows。要
  它得先有真沙箱。
- **自定义挂载点、MCP、技能写入、工具元数据层**（`additional_kwargs` 里那套
  `error_type` / `recoverable_by_model`）：各自需要自己的设计。
- **`extensions_config.json`**：`loader.load_extensions()` 至今没有被任何地方调用，本片不碰它
  ——现在把工具塞进去等于把一个半成品坐实成契约。
- **按需装配工具**（按 `group` 过滤）：现在只有一个消费者，加分组就是给还没出现的需求写机制。
  `ToolConfig` 是 `extra="allow"` 的，将来加它是纯增量。
- **每部署的工具参数**：本片用工厂的默认值。真要做「按部署配每个工具的旋钮」，那是
  「每请求/每部署参数从哪来」那一片的事，届时给 `use:` 保持工厂形态即可，配置格式不用推翻。

## 遗留债（验收时实测到的）

**删会话不删文件。** `DELETE /threads/{id}` 会清掉 journal 与 checkpoint，但
`backend/.evaai/user/{会话}/` 原样留着（实测：删掉全部会话后目录仍在）。这条**不做**不是
漏了，而是它需要一个决定：`/input` 是用户上传的原件、`/output` 是交付成品——「删掉这段对话」
要不要连带删掉用户的东西，答案并不显然（多半是**不要**，至少 `/output` 不该删）。所以它属于
单独一片：要么给会话加「同时删除文件」的显式选项，要么给沙箱加保留期（像
`prune_checkpoints` 那样）。在此之前，删会话只删记忆与记录。

**这条债在「第一条消息建目录」之后更明显了**：现在每个会话都会留下三个目录，包括从头到尾
没碰过文件的那些。若短期不打算做上面那片，退路是给空目录加一条清理（「目录存在但三个都空
且 journal 已删」即可回收）。
